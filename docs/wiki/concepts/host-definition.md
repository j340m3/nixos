# Host definition idioms (dendritic)

The canonical trio (Doc-Steve Comprehensive Example, verified in repo source
2026-10-21):

**1. config-builder helpers in a feature module** (`modules/nix/flake-parts [FL]/lib.nix`):
```nix
{ inputs, lib, ... }: {
  options.flake.lib = lib.mkOption { type = lib.types.attrsOf lib.types.unspecified; default = { }; };
  config.flake.lib = {
    mkNixos = system: name: { ${name} = inputs.nixpkgs.lib.nixosSystem {
      modules = [ inputs.self.modules.nixos.${name} { nixpkgs.hostPlatform = lib.mkDefault system; } ]; }; };
    mkDarwin = system: name: { ${name} = inputs.nix-darwin.lib.darwinSystem { /* same shape */ }; };
    mkHomeManager = system: name: { ${name} = inputs.home-manager.lib.homeManagerConfiguration {
      pkgs = inputs.nixpkgs.legacyPackages.${system};
      modules = [ inputs.self.modules.homeManager.${name} { nixpkgs.config.allowUnfree = true; } ]; }; };
  };
}
```
Note: the helper reads the *aspect* `flake.modules.nixos.<host-name>` — the
host is declared **via its module value, not a path**. No `specialArgs` at
all (values shared via top-level config; dendritic README anti-pattern
"specialArgs pass-thru").

**2. per-host flake-parts.nix (the "self-declaration" one-liner)**:
```nix
{ inputs, ... }: { flake.nixosConfigurations = inputs.self.lib.mkNixos "x86_64-linux" "homeserver"; }
```

**3. per-host configuration.nix (the host as a feature)**:
```nix
{ inputs, ... }: {
  flake.modules.nixos.homeserver = {
    imports = with inputs.self.modules.nixos; [ system-cli systemd-boot impermanence ];
  };
}
```
Hardware (`hardware.nix`, `filesystem.nix`) stays as files inside the host
feature dir, imported by it. The host dir may also carry collector-style
extra aspect definitions (e.g. `services/syncthing/syncthingDevices.nix`
merging into `flake.modules.nixos.syncthing`).

## Variants in the reference repos

- **mightyiam/infra**: imports auto but filtered
  (`(import inputs.import-tree).filterNot (lib.hasSuffix ".pkg.nix") ./modules`);
  modules declare their own options (`nixos.base`, `nixos.pc =
  config.nixos.base`), no flake.modules reliance for its own tree; flake.nix
  auto-generated by denful/flake-file.
- **drupol/infra** (`modules/hosts/apollo/default.nix`): uses the `den`
  framework instead of raw flake.modules:
  ```nix
  den.aspects.apollo = {
    includes = with den.aspects; [ ai-ollama base (facter ./facter.json) desktop dev openssh ... root ];
    nixos = { boot = { /* inline NixOS config */ }; /* ... */ };
  };
  ```
  plus `modules/dendritic.nix` wiring `inputs.den.flakeModules.dendritic` and
  `den.schema.user.classes = [ "homeManager" ]`.
- **this repo (current)**: `modules/hosts/<name>/flake-parts.nix` one-liner →
  `self.lib.mkNixos "<name>"` (modules/flake/lib.nix), which passes
  `specialArgs = { inputs; constants = import global/constants.nix; }` and
  imports the host **directory** `modules/hosts/${host}` as a plain NixOS
  module tree. Very close to the dendritic trio already; the pattern move is:
  host modules become `flake.modules.nixos.<name>` values (keyed by aspect
  name, not path), and specialArgs go away.

## Trade-offs

- **Import-as-enable vs enable options**: dendritic README says importing a
  module should enable its feature; keep `enable` only when the module is
  imported while its effect must stay optional (cf. this repo's
  `upgradeHealth.enable` — it *is* imported via common everywhere, so per-host
  `enable = true` is exactly the dendritic-legitimate enable case).
- **Keying hosts by aspect name**: renames the host = renames the aspect;
  `nixosConfigurations.<name>` and the option share one name (fewer moving
  parts than path-keyed dirs).
- **systems choice inline**: `mkNixos` takes the system; hosts with different
  arch (slinky aarch64) pass their own string — no cross-host, mkDefault
  keeps it overridable.
